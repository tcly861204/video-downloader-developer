# 2026-08-31

## analytics.rs 设备 ID 改为机器级稳定 ID
- 需求：`device_id` 不能每次安装生成新 ID，要取用户电脑的唯一 ID。
- 改动：
  - `src-tauri/Cargo.toml` 新增依赖 `machine-uid = "0.6"`。
  - `src-tauri/src/analytics.rs`：删除「随机 UUID 存配置文件 device_id」的逻辑，`device_id()` 改为 `machine_uid::get()`（Windows 读注册表 MachineGuid / macOS gethostuuid 硬件 UUID / Linux /etc/machine-id），失败时退化为随机 UUID。同时移除不再使用的 `Manager` import。
- 验证：`cargo check` 通过，无警告。
- 注意：Windows 上 MachineGuid 随系统安装生成，重装系统会变；macOS 的 gethostuuid 重装系统也不变。
- 备选方案（未采用）：如需跨重装系统也稳定，可改用 SMBIOS 主板 UUID（Win32_ComputerSystemProduct.UUID）。

## 封禁机制：服务端裁决 + 客户端执行
- 需求：剔除指定用户，禁止其使用桌面软件。
- 方案：新增 `src-tauri/src/gate.rs`（客户端访问控制模块）：
  - 启动延迟 800ms 后 POST `https://stock.tcly-club.top/api/gate`，携带 `{id: device_id(), v, os}`；
  - 服务器返回 `403 {status:"blocked", reason}` → 弹窗（tauri-plugin-dialog blocking_show，独立线程）用户确认后 `app.exit(0)`；
  - 之后每 10 分钟复查一次（RECHECK_INTERVAL_SECS），用于踢出正在使用的被封设备；
  - 网络错误/非 JSON 一律 fail-open 放行；`cfg!(debug_assertions)` 跳过。
  - `analytics::device_id()` 改为 `pub(crate)` 供 gate 复用；lib.rs 的 setup 中调用 `gate::init(app.handle())`。
- 服务端：`functions/api/gate.js`（Cloudflare Pages Function，本地已创建），BLOCKED Set 放设备 ID，量大可换 KV。
- 局限（已告知用户）：客户端校验可被绕过（改注册表 MachineGuid、屏蔽域名、patch 二进制），属威慑而非硬安全；硬限制需把核心操作放到服务端鉴权。

## 封禁机制升级：BLOCKED 集合 → D1 表字段（本次会话二稿）
- 需求：不在代码里写死名单，改为 launch_events 表加字段，gate 读字段判定。
- 改动：
  - `functions/api/launch.js`：头注释更新建表 SQL，新增 `is_banned INTEGER DEFAULT 0`、`ban_reason TEXT`、`banned_at TEXT` 三字段，并给出旧表 ALTER TABLE 迁移 SQL。
  - `functions/api/gate.js`：删除 BLOCKED 硬编码逻辑，改为查 D1：`SELECT ban_reason FROM launch_events WHERE device_id=? AND is_banned=1 ORDER BY id DESC LIMIT 1`；有行即 403。**关键设计**：判定规则是「存在任一 is_banned=1 的行」而非"最新一行"——因为事件表每次启动插新行（默认 0），查最新行会让封禁失效。查询失败 fail-open。保留 BLOCKED 作空集合应急兜底。
  - 新增 `functions/api/ban.js`：管理接口 POST /api/ban，body {secret, id, action:"ban"|"unban", reason}，校验环境变量 BAN_SECRET（需在 CF 控制台配置）；ban 时 UPDATE 所有行 is_banned=1，若 0 行（从未上报过）则 INSERT 占位记录保证立即生效；unban 置 0。
- 验证：三个 js 均通过 `node --check`。
- 部署注意：老表需先在 D1 执行一次 ALTER TABLE 加字段；BAN_SECRET 需在 Cloudflare 控制台配置。

## 封禁方案升级三稿：事件/状态分表（launch_events + devices）
- 需求：用户指出 launch_events 是事件表（每次启动一行），封禁状态放里面语义混乱，应建新表存状态。
- 新表 `devices`（一台设备一行）：device_id PK、is_banned、ban_reason、banned_at、last_seen_at、created_at。
- 改动：
  - `launch.js`：头注释改为双表建表 SQL + 旧字段迁移说明；写入改为 `env.db_framecatch.batch([...])` 原子写两张表（事件 + devices upsert last_seen_at，**不覆盖 is_banned**——这是关键，封禁状态不被启动冲掉）。
  - `gate.js`：查询改为 `SELECT is_banned, ban_reason FROM devices WHERE device_id=?`，查无记录放行。不再有"存在任一封禁行"的判定坑。
  - `ban.js`：ban 用 UPSERT（`ON CONFLICT(device_id) DO UPDATE`），从未上报的设备也能直接建行生效，**删掉了原来的占位行 hack**；unban 直接 UPDATE 置 0。
- 新增 `scripts/verify-gate-sql.py`：用本地 SQLite 模拟 D1 全链路断言（10 次启动事件累积/状态单行、封禁、封禁后启动不冲状态、解封、未登记设备放行），可作回归工具。
- 验证：三个 js 通过 `node --check`；Python 模拟 SQL 全部断言通过。
- 部署注意：D1 需要新建 devices 表（SQL 在 launch.js 头注释）；launch_events 旧 is_banned 字段可忽略不再读取。
